# Contract Knowledge Management

Use this reference when changing any public n8n adapter contract in `/home/lsk/projects/n8n`.

## What Counts As A Contract

- n8n webhook path or method.
- Required auth header or token semantics.
- Request payload fields, required fields, accepted aliases, validation rules, and unsupported fields.
- Response body shape and HTTP status codes.
- JSON Schema, OpenAPI, workflow catalog, or any file consumed by external applications.
- Human-facing usage/deployment docs that external integrators or operators use to call the workflow.

## Source-Of-Truth Rules

- Use machine-readable contracts for external application discovery.
- External applications discover the contract at `GET http://127.0.0.1:5678/webhook/contracts/openapi.json`.
- External applications select OpenAPI human-readable language with `GET /webhook/contracts/openapi.json?lang=en|ru`; omitted `lang` returns the deployment default, `N8N_OPENAPI_DEFAULT_LOCALE` or repository default `ru`.
- OpenAPI localization changes only human-facing metadata such as `title`, `summary`, `description`, response descriptions, and example summaries. Do not localize paths, `operationId`, schema names, payload field names, enum/const values, error codes, or auth headers.
- External applications discover email templates at `GET http://127.0.0.1:5678/webhook/contracts/email-templates.json`.
- Email template params that can carry credentials, generated passwords, tokens, or other secrets must be marked with `sensitive: true` in `contracts/email-template-catalog.json` and reflected in `contracts/email-template-catalog.schema.json` plus OpenAPI `EmailTemplateParam`. Workflows that render or send such templates must disable saved execution data.
- Execution endpoints stay separate from the discovery endpoint and remain protected by `X-ServiceDesk-Token` when they perform actions.
- Zabbix problem updates use `problemUrl` as the multi-Zabbix identity source, parse `eventid` and `triggerid`, verify with `problem.get`, and append `message + "\n"` through `event.acknowledge`; do not add a custom timestamp because Zabbix displays the operation time itself.
- Zabbix problem status lookup uses `problemUrl` as the multi-Zabbix identity source, parses `eventid` and `triggerid`, reads `event.get` first, falls back to `trigger.get` when the event is unavailable, and returns only `problem`, `resolved`, or `ok`.
- In Zabbix status lookup, `resolved` means the original event is available and has recovery evidence; `ok` means the original event is no longer available but current trigger value is OK.
- Zabbix problem wait is async-only at `POST /webhook/zabbix/problem/wait`. It composes `getZabbixProblemStatus`, requires `problemUrl`, `poll_interval_minutes`, `timeout_minutes`, and `invocation.extensions.async_callback`, and uses action_id `wait_zabbix_problem_status`.
- Zabbix problem wait returns terminal `status` values `ok`, `resolved`, `problem`, or `ERROR`. Timeout is represented as factual `status: problem` with `timed_out: true`, not as a separate business status.
- Zabbix API tokens are configured by origin through `ZABBIX_API_TOKENS_BY_ORIGIN`; use `ZABBIX_API_URLS_BY_ORIGIN` when the UI origin is not reachable from the n8n container.
- In live n8n Code nodes, do not rely on global `fetch`; use `this.helpers.httpRequest` for outbound HTTP calls from workflow JavaScript.
- ServiceDesk runbooks are dual-use through one canonical HTTP endpoint. Direct callers use the OpenAPI operation; `serviceDeskAgents` Kafka workers wrap the same call and pass `invocation.extensions.async_callback`.
- Async runbook completion uses the canonical ServiceDesk `ExternalEvent` contract. `http_callback`, `kafka_event`, and `both` are result transports, not separate business runbook contracts.
- OpenAPI must publish transport security metadata in `x-transport-security`. HTTP webhook/callback URLs are admin-configured; local/dev may use `http://127.0.0.1`, while shared/staging/production should use HTTPS URLs selected by the administrator.
- Async HTTP callback URLs must pass the same policy in code, OpenAPI and docs: `http`/`https` only, no user/password credentials, same origin and same or nested path as `ORCHESTRATOR_PUBLIC_URL` when configured, and HTTPS required in production outside local/dev loopback or compose-host exceptions.
- Do not copy `N8N_WEBHOOK_TOKEN` into workflow item state or callback payloads. Code nodes that need to call internal protected n8n webhooks must read `N8N_WEBHOOK_TOKEN` locally from env at the node where the outbound request is made.
- Kafka result delivery is not HTTPS. Document and test Kafka security as broker credentials/ACL with production support for `SASL_SSL` and `SSL`/mTLS; do not put Kafka secrets or TLS materials into workflow JSON, contracts, docs, or payload examples.
- For this project, local Kafka result delivery defaults to topic `external.events`; stage4 uses the n8n Kafka credential named `Local Redpanda Kafka` in the local stand.
- HTTP callback delivery uses `X-ServiceDesk-Callback-Token`; n8n reads the token from `INTEGRATION_CALLBACK_TOKEN__<NORMALIZED_SOURCE>` first and then `INTEGRATION_CALLBACK_TOKEN`.
- Stage4 currently implements a safe stub that emits terminal `success` immediately after accepting an async request. Preserve the ExternalEvent contract when replacing the stub with real long-running logic.
- Email wait by ticket uses a two-workflow model: `Email: индекс входящих писем` fills Postgres table `n8n_mail_index` from IMAP, and `Email: ожидание письма по номеру заявки` searches that index through `POST /webhook/email/wait-for-ticket`.
- Email wait result statuses are only `OK`, `MULTI_MAIL`, `DELIVERY_FAILED`, and `NOT_FOUND`. `DELIVERY_FAILED` is best-effort NDR/bounce detection and must not be documented as a guaranteed cross-mail-system delivery proof.
- Email wait direct HTTP mode is only for short smoke/manual waits and is capped at `timeout_minutes <= 5`; 60-minute agent waits must use `invocation.extensions.async_callback` and canonical ExternalEvent delivery.
- CMDBuild provider context lookup is read-only at `POST /webhook/cmdbuild/provider-email-context`. It searches active `routerG` by exact `Description == hostname`, requires `email`, `contract`, `ipaddress`, and `Location`, resolves `IpAddress.Description`, `Room.Description`, and `Room.Floor -> Floor.Building -> Building.City`, and returns `provider_email`, `contract`, `ip_address`, `location`, and `city`.
- CMDBuild test credentials must stay in n8n `httpBasicAuth` credential `Local CMDBuild Admin Test`; do not commit `admin/admin` or production CMDBuild passwords to workflow JSON, scripts, OpenAPI examples, docs, or logs.
- HR manager verification is read-only at `POST /webhook/hr/verify-manager`. It requires employee full name and claimed manager full name, accepts `relation_type=administrative|managerial|both` with default `both`, returns `OK` only for a single confirmed employee-manager pair with verified tabular numbers for both participants, and returns business `ERROR` for not found, duplicate names, no confirmed relation, missing employee tabular number, or missing manager tabular number. `OK` must include top-level `employee_id` and `manager_id`.
- HR API credentials must stay in n8n `httpHeaderAuth` credential `HR API Header Auth`; configure the base URL through `HR_API_BASE_URL` and do not commit HR API tokens, employee personal data samples, or production HR URLs into workflow JSON, scripts, OpenAPI examples, docs, or logs.
- HR applicant participant verification is read-only at `POST /webhook/hr/verify-applicant-participant`. It requires `applicant_full_name`, `employee_full_name`, and `manager_full_name`, accepts camelCase aliases, performs only normalized string comparison, and returns `matched_role=employee|manager|both` or business `ERROR` `applicant_not_participant`.
- HR applicant participant verification must not be documented as proof that the people exist in HR/AD or that the manager relation is valid. Use `verifyEmployeeManager`, HR lookup, or AD lookup workflows when source-system identity proof is required.
- AD user login lookup is read-only at `POST /webhook/ad/user/login-lookup`. It requires `full_name` and `employee_id`, accepts camelCase aliases, uses exact LDAP equality on configurable attributes, and returns business `ERROR` for not found, duplicate users, empty login attribute, or empty email attribute.
- AD lookup defaults are `displayName` for full name, `employeeID` for tabular number, `sAMAccountName` for login, and `mail` for email. Runtime env can override them with `AD_FULL_NAME_ATTRIBUTE`, `AD_EMPLOYEE_ID_ATTRIBUTE`, `AD_LOGIN_ATTRIBUTE`, and `AD_EMAIL_ATTRIBUTE`; callers can override per request. `AD_BASE_DN` is required unless `base_dn` is passed.
- AD password reset is mutating at `POST /webhook/ad/user/reset-password`. It requires `login`, accepts `password_length`, `allowed_chars`, `login_attribute`, `base_dn` and camelCase aliases, generates a password, finds exactly one AD user by login, updates `unicodePwd`, sets `pwdLastSet=0`, and returns the password only on `status: OK`.
- AD password reset must be protected by external ServiceDesk/orchestrator approval before n8n call, must use LDAPS/TLS, and must disable saved execution data. The generated password is a secret: do not log/store it, include it in tickets/screenshots, or send it through callback/Kafka result payloads. Happy-path smoke is allowed only on an approved disposable AD account.
- AD password reset process is mutating at `POST /webhook/ad/password-reset/process`. It composes applicant participant check, HR manager verification, AD employee/manager lookup, AD password reset, and templated email notification. It must stop on the first failed step and return `status: ERROR`, `failed_step`, `password_changed`, `notification_sent`, and sanitized completed `steps`. It must never return the generated password. If notification fails after reset, return `ERROR` with `password_changed: true` and `notification_sent: false`; do not attempt rollback in n8n.
- AD credentials must stay in n8n `ldap` credential `MS AD LDAPS`; production should use LDAPS/TLS with valid CA trust. Do not commit bind DN passwords, CA private material, AD user samples from production, base DN secrets, or raw LDAP filters into workflow JSON examples, docs, logs, or callback payloads.
- Provider channel repair monitor is async-only at `POST /webhook/provider/channel-repair/monitor`. It requires `host`, `problemUrl`, `service_request`, `poll_interval_minutes`, `timeout_minutes`, and `invocation.extensions.async_callback`; `action_id` must be `monitor_provider_channel_repair`.
- Provider channel repair monitor composes existing contract endpoints instead of duplicating their logic: CMDBuild provider context, templated email dispatch, Zabbix problem status, and the Postgres mailbox index populated by the email collector.
- Provider channel repair monitor checks Zabbix first on every polling iteration. `ok` or `resolved` returns terminal `RESOLVED`; otherwise it searches email by `service_request` and returns `OK`, `MULTI_MAIL`, `DELIVERY_FAILED`, `NOT_FOUND`, or `ERROR` through canonical ExternalEvent delivery.
- For dynamic polling waits, generate Wait nodes with `resume: specificTime` and `dateTime: ={{ $json.next_wait_at }}`. Keep `next_wait_seconds` as a diagnostic field. The local n8n 2.21.7/Node 24 stand can still emit `TimeoutNegativeWarning` after Wait resume even when the workflow completes; this is a runtime limitation to verify against the customer's n8n version or suppress through runtime configuration after approval.
- Use runbook docs for operators and human integrators.
- Use workflow exports for n8n import/runtime behavior.
- Use project-local skills only for agent behavior and project-specific working rules.
- Avoid copying large schemas into `SKILL.md`; link to repository files or summarize the rule here.
- For development, email templates are versioned in the current GitHub repository. For production, the same contract files and workflow exports should be supplied from GitLab rather than edited manually in n8n UI.
- n8n workflow diagnostics must support `N8N_WORKFLOW_DEBUG=off|Basic|Verbose`, mask secrets and large/sensitive payloads, write through the normal stdout/stderr logging path, and require a second production sink such as syslog, collector/agent/sidecar, ELK/OpenSearch, or a platform log collector. Local Docker `json-file` alone is not production-ready.

## Readiness Checklist

- Contract URL or file is documented.
- Execution URL is separate from contract/discovery URL.
- Auth header and token source are explicit.
- Request and response examples match the workflow implementation.
- Negative cases are documented when the workflow returns structured errors.
- Smoke checks cover unauthorized and happy-path behavior when auth is involved.
- Workflow exports include inline description and per-node Sticky Notes.
- `node scripts/apply-workflow-inline-documentation.mjs --check` passes.
- Run `node scripts/test-contracts.mjs` with generator drift checks before importing contract-changing workflows into live n8n.
